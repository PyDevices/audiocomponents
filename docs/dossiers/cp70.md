# Accuracy Dossier — `cp70` (Yamaha CP-70 Electric Grand)

**Module:** `audiocomponents/lib/audioinstruments/cp70.py` (127 lines)
**Proposed grade:** **literature**, argued DOWN from the survey's **gold** —
same direction the charter asks for (cr78 held down rather than inflate on a
partial capture; clavinet was already argued down for the identical reason:
no reachable capture of the exact real machine). Reasoning in §1.
**Reference settings (D3):** the sibling CP-80 capture is known-settings
(velocity-layered, per-note); the one real CP-70 capture is not, and its own
creator says so.

## 1. Reference and grade

The survey merged two passes and landed on gold, built from three legs: a
capture of the literal CP-70 (Pianobook "David's CP70"), a much stronger
capture of the CP-80 sibling (Greg Sullivan's E-Pianos, CC BY 3.0), and an
MIT-licensed schematic explicitly covering "CP-70 and CP-80" as one preamp
family. Re-checked this session; the grade does not hold, for a reason the
brief itself points at: **the CP-80 is not the same instrument.**

**The one real CP-70 capture is not usable as a precision oracle.** Its own
creator describes the session as "very impromptu and imprecise," with
clipping from the board into the interface and "slightly out of tune
strings" (https://www.pianobook.co.uk/packs/davids-cp70/, re-fetched this
session — quoted in full above). That is a legitimate rough A/B reference;
it is not a source you derive attack-transient or spectral-envelope numbers
from with confidence, which is exactly what this dossier's acceptance
criteria need.

**The CP-80 capture is real, well-documented, and permissively licensed —
and it is a different-sized instrument.** 73 keys vs 88
(https://en.wikipedia.org/wiki/Yamaha_CP-70, CC BY-SA 4.0, re-fetched this
session). The brief flags string length and range as the open question; this
session could not close it cleanly. One aggregated web-search claim (not
independently confirmed by visiting its own source) asserts the CP-80's
larger harp gives it longer strings across most of the range and a
"richer... more open" sound where "the CP70 sounded tighter." Visiting the
two forum sources behind that search turned up something closer to a wash: a
HandWiki mirror of the Wikipedia article states plainly "the page doesn't
specify different string lengths between the two models," and a
vintagesynth.com thread (https://forum.vintagesynth.com/viewtopic.php?t=75531,
no license stated, read for facts only) describes only that CP-70 notes
below the second F# use a single string, and two strings above it — a real,
useful fact, but not a length comparison against the CP-80. **Whether the
CP-80's strings are simply longer at the same pitches, or the same, is not
established by anything this session actually reached.** Given that the
identifying "clangy, stiff bass" trait in `docs/phase2-listening-guide.md`
is attributed specifically to the CP-70's shortened bass strings, measuring
that trait against a capture of a physically different harp is exactly the
kind of substitution the reference hierarchy exists to catch.

**What does clear, and clears well, is literature.** The MIT-licensed
schematic project is unusually strong for a tier-2 source — not a scanned
service manual nobody can read, but a hobbyist restoration project (owns
multiple originals) with a redrawn, clickable SmartPDF schematic, Altium
files, TINA-Spice simulation files, and *measured* frequency-response plots
of the tone circuit at various Brilliance/Bass/Mid/Treble settings
(https://github.com/tjscientist/Yamaha-Preamp-Work, MIT, license read at
`.../blob/main/LICENSE` and README read in full this session). It explicitly
states the CP-70 and CP-80 preamp is the same circuit, which is a much
narrower, better-supported claim than "the whole instrument is close
enough" — the preamp (buffering, tone controls, tremolo) is shared; the
mechanical string/harp/pickup assembly, where the size difference lives, is
not addressed by this source. Two more schematic-tier artifacts were newly
found and confirmed real this session but not readable: `ep-service.nl`
hosts a "Yamaha CP-80 Overall Circuit" PDF that is a genuine 5-page scanned
engineering drawing (CCITT-fax image data, 7184×1167 px/page, dated 2007,
AccXES wide-format-scanner output — confirmed by fetching the file directly,
not just its listing page), plus a block diagram and wiring diagram; all are
images with no text layer, so nothing in them could actually be read this
session. The Yamaha factory service manual (CP80D/CP80M/CP70D/CP70M/CP60M,
63 pages + a 38-page parts list, exact models named) is confirmed to exist
at elektrotanya.com and mirrored at Scribd, both still gated behind a
click-through/subscription this session did not complete — re-tried by
direct `curl`, which returned the "Download is being processed" HTML page
again, not a PDF. **New PDF tooling was available this session (`pypdf`)
that the prior survey pass lacked, and it changed the finding slightly, not
the outcome:** the reachable Yamaha CP-70B Operating Manual PDF
(synthfool.com, fetched in full, 3.3 MB, 18 pages) has *zero* extractable
text on every page checked — it is a scanned image, not merely un-OCR'd
text. The blocker isn't missing tooling, it's that these archives are
picture scans; OCR was not attempted (no `tesseract`/`pdftoppm` available in
this environment, and installing them was judged out of scope for a
research pass).

**No open-source emulator changes this.** `beneke7/cp80-model` (AGPL-3.0,
license file read directly this session) is a real, carefully-built
modal-synthesis physical model with its own reference-fitting tooling
(`tools/cal.py`, `tools/fit_hammer.py`, `tools/attack_probe.py` all
reference a `CP80_REFERENCE_DIR` it calibrates against) — a genuine
proxy-tier candidate for later, output-only measurement. Its README
advertises prebuilt VST3/AU/standalone binaries on a releases page; the
releases API returned none this session, so there is currently nothing to
measure without building from source, which is a Station C task, not this
one. `edwin-oetelaar/CP70_preamp` remains what the survey found it to be: a
modern KiCad art-project preamp replacement, license unverified (no
LICENSE file, confirmed by listing repo contents this session), useful only
for its architecture claim (72 individually-buffered piezo channels).

**Grade: literature**, resting on the MIT-licensed preamp schematic plus
Wikipedia's mechanical description (piezo pickups on the harp, no
soundboard, hammer action), corroborated but not upgraded by the CP-80
capture and the rough real-CP-70 capture, both usable as directional A/B
checks rather than the numeric basis for acceptance criteria.

## 3. What the machine is, mechanically

A genuine small grand piano action — wooden keys, felt hammers, steel
strings — with the soundboard omitted and the strings shortened (bass
strings 26¾ in / 67.9 cm, against roughly 7 ft on a concert grand). Piezo
pickups mounted on the metal harp read the strings directly, guitar-pickup
style (Wikipedia, cited above). Below the second F#, notes are single-strung;
above it, double-strung like a piano's unison course
(forum.vintagesynth.com, cited above). The preamp stage (buffering, tone
shaping, tremolo) is documented by the MIT schematic as shared between the
CP-70 and CP-80. The real front panel carries Hi/Mid/Low EQ (Brilliance-type
controls) and a stereo tremolo with rate and depth
(forum.vintagesynth.com); later revisions (CP-70D/80D) added a graphic
equalizer and an effects loop (Wikipedia). **No onboard chorus ever
existed** — Tony Banks' signature CP-70 tone on Genesis' "That's All" came
from running it into an outboard Boss chorus pedal
(`docs/phase2-listening-guide.md`, sourced there to Wikipedia's "That's All"
and "Tony Banks" articles, not re-verified independently this session).

## 4. Voice structure and polyphony vs the module

Fully polyphonic hardware: every string/course has its own dedicated piezo
pickup and preamp channel, no shared circuitry, no voice-stealing —
confirmed independently by the CP70_preamp hobbyist project's description of
a 72-channel individually-buffered pickup design for the 73-key instrument
(https://github.com/edwin-oetelaar/CP70_preamp, license unverified,
informational only). Effective polyphony is the full 73-key range.

`cp70.py:64` sets `MAX_VOICES = 12` — the most constrained of the five
Phase 2 pianos relative to its own reference, per the survey's own note, and
confirmed again here: 12 held keys against 73 independent strings is a large
mismatch, and it runs the *opposite* direction from the roadmap's `MAX_VOICES
= 1` monophonic cases. Per roadmap §3, *"where a reference says the hardware
had more voices than the module gives it, that is a legitimate rebuild"* —
raising `MAX_VOICES` toward something that survives a heavily pedalled
chord voicing is in scope for Station B, bounded by the MCU budget (§6).

**A unit-mixing detail worth carrying into Station B, read from the code:**
`voices` (`cp70.py:62`) is keyed by held note, and the cap at `cp70.py:81`
(`if len(voices) >= MAX_VOICES: steal_oldest()`) counts held *keys*, not
raw `synthio.Note` objects. Each key spawns 2 or 3 Notes — 3 with the
default patch's Chorus macro on (two detuned string oscillators plus the
hammer transient, `cp70.py:96-104`), 2 with Chorus off. So a fully pedalled
12-note chord under the shipped default patch presses up to 36
`synthio.Note` objects at once, not 12 — the same units-mixing pattern
`tr808.md` §3 flagged in `_support.trigger_voice` (audiocomponents#10), even
though `cp70.py` doesn't call that helper; it inlines an equivalent, simpler
check that doesn't account for the incoming press's own Note count either.
Not a defect to fix here — a fact Station B needs before sizing a raised
`MAX_VOICES` against real oscillator budget.

## 5. Modeling approach and a structural finding

**Current shape, read from the code:** one long-tail string voice
(`WAVE_STRING`, a full `1/n` series to the 39th harmonic, `cp70.py:43`) per
oscillator, layered with a short, sparse `WAVE_HAMMER` transient
(`cp70.py:42`, harmonics 1/3/5/9) through a shared one-pole lowpass driven
by the Brilliance macro (`cp70.py:90-91`). When Chorus is above 0.01 — true
of the shipped default patch, whose macro value is 64/127 — the string
voice becomes two detuned, oppositely-panned oscillators instead of one
(`cp70.py:97-100`).

**The Chorus macro is conflating two physically different things.** The
comment at `cp70.py:96` calls this "Chorus simulation," and the listening
guide independently flags it: real CP-70s had no onboard chorus at all, and
the guide's own first listening instruction is "patch 0 ships with Chorus at
64/127. Pull Chorus to zero before judging this"
(`docs/phase2-listening-guide.md`, cp70 §1 and §4). But the same
dual-oscillator machinery the code uses for "Chorus" is also the only
plausible place in this model for the real hardware's double-strung unison
course above the second F# (§3) — a physical feature of every note in most
of the compass, present with the pedal-chorus macro all the way at zero.
Today the model has no way to be both dry (no pedal effect) and doubled
(true to the stringing) at once. **Proposed structural change**, justified
by the vintagesynth stringing fact and the listening guide's own dry-check
instruction: give every note above the stringing break a small, fixed,
always-on unison detune independent of the Chorus macro, and default Chorus
itself to 0 (matching "no CP-70 ever shipped with onboard chorus") — a
patch-0 default change, not a new macro. This uses `MACRO_LABELS` room that
already exists (9 of 16 used) without needing it.

**Velocity does not shape tone**, only level: `amp = volume * value0`
(`cp70.py:85`), confirmed independently by `docs/phase2-listening-guide.md`
§5's own read of this file ("velocity doesn't shape tone"). Listening guide
trait 3 ("real hammer attack, real touch") wants a harder hit to sound
harder in colour, not just louder — general piano acoustics, not a CP-70-
specific citation the guide could source, but physically well-founded and
directly actionable: couple `hammer_lvl` or `brilliance` to velocity rather
than only `amp`.

**Toolkit upgrade candidates**, tied to what §3 documents about the real
panel: the hardware has Hi/Mid/Low EQ, not a single lowpass — `synthio`
already exposes `FilterMode.PEAKING_EQ`
(`audioif/src/cpython/synthio.py:33`), so a genuine 3-band EQ (two peaking
stages plus the existing lowpass as the "Brilliance" high shelf-ish control)
is directly buildable and would need at most two new macros if the panel's
Hi/Mid/Low is to be independently addressable, well inside the 16-macro
ceiling. `audiodynamics` could shape the hammer transient's attack more
expressively than the fixed 0.1 s `hammer_env` decay does today. No
convolution is proposed anywhere in this model — no cabinet or room IR is
appropriate for an instrument whose defining trait is that it has *no*
acoustic resonating body (§2's "no bloom" trait) — so no
`audioconvolve.FRAMES` latency is incurred by any change proposed here.

## 6. MCU budget and macro budget

`MACRO_LABELS` uses 9 of 16 (`cp70.py:9-12`); `PATCHES` uses 1 of 128
(`cp70.py:29-31`). Room exists for the EQ-split macros in §5 without
pressure on the ceiling.

Raising `MAX_VOICES` toward the hardware's ~73-key ceiling is not free: at
today's 2–3 Notes per key, even a modest rise (say, toward 24) triples peak
oscillator count from the current worst case of 36 to roughly 72. **A
`" - lean"` patch is likely warranted if `MAX_VOICES` rises meaningfully** —
consistent with roadmap §7.1's escape valve — but the exact cutoff is a
Station B measurement against real per-voice cost on a small target, not a
number this dossier can responsibly invent.

## 7. Proposed acceptance criteria

**The measurement constraint that governs the other four Phase 2 pianos
does not fully apply to this one — read directly from the envelope, not
assumed.** `cp70.py:87` sets `sustain_level=0.0` on the main voice envelope
(and `cp70.py:88` sets the same on the hammer transient). Issue #16's own
table of "sustaining pianos [that] hold a level indefinitely without a
note-off" lists rhodes (0.2), wurlitzer (0.2), pianet (0.1), and clavinet
(0.1) — **cp70 is not on that list, and the code confirms why**: like every
Phase 1 drum voice, a `cp70` note decays fully to silence on its own once
`decay_time` elapses, whether or not a note-off ever arrives. This matches
the physical reality checked in §3 and the listening guide independently:
none of the five identified cp70 traits in
`docs/phase2-listening-guide.md` (no-bloom, clangy bass, hammer attack,
chorus shimmer, tremolo) concern how the note *ends* — unlike its four
siblings, whose §1 tells all open with "does the note die when you let
go?" This instrument's identity lives entirely in attack and sustained
tone, both fully renderable today.

**A separate, real tooling gap, found this session and not previously
recorded:** `tools/render_component.py`'s `oneshots`/`kit`/`phrase`/
`transitions` modes are all built around `NOTE_MAP`
(`tools/render_component.py:89,102,108,135` — `note_map = getattr(module,
"NOTE_MAP", ())` at line 86), which `cp70.py` correctly does not declare
(it is melodic, not percussion, per `docs/audio-components.md`'s NOTE_MAP
discriminator). So although cp70's decay is measurable in principle, **no
existing render mode can actually produce a held single-note WAV for it** —
Station C needs a melodic-instrument mode (a fixed pitch, held for its full
`decay_time`, analogous to what `oneshots` does per `NOTE_MAP` entry) before
any of the "measurable now" rows below can be checked. This sits alongside,
not instead of, issue #16.

| Criterion | Method | Status |

an actual measured render — none was taken this session (Station A does not
download the CC BY 3.0 CP-80 samples; obtaining them for Station C
