# Accuracy Dossier — `tr909` (Roland TR-909 Rhythm Composer)

**Module:** `audiocomponents/lib/audioinstruments/tr909.py` (258 lines)
**Proposed grade:** **gold.** A known-settings hardware capture pack was
reached, downloaded in full, and measured directly — the one case in the
program so far where the acquisition gap that limited `tr808` (Splice
account gate) did not recur.

## 1. Reference and grade

**Primary — capture:** Audiorealism TR-909 Ultimate Sample Pack, 96 kHz/24-bit
edition (https://audiorealism.se/TR-909-SamplePack). Direct download link
found on the page (`https://audiorealism.se/downloads/TR-909-96kHz-24bit.zip`,
200,600,165 bytes, no account gate), fetched whole this session. 849 WAV
files extracted; 848 measured cleanly by `tools/measure_hits.py`
(`.reference-captures/tr909/stats.json`; one file skipped, see script
stderr — not investigated further). The pack's own `Readme.txt` states:
"853 samples from the Roland TR-909 Drum Machine... recorded at 96kHz with
32-bit float accuracy... sampled from their individual outputs to prevent
any clipping, with the part volume set to 50%." Provenance is as strong as
the hierarchy asks for: **known knob settings encoded in every filename**
(e.g. `BassDrum909-tune050-attack100-decay100.wav`), full 5×5×5 grids for
Bass Drum (tune/attack/decay) and Snare (tune/tone/snappy), full 11×11
grids for each tom (tune/decay), and 11-step tune sweeps for Crash and
Ride — this is a **known-settings single-hit capture** in the vision §4
sense, not a statistical cross-check like `tr808`'s fallback pack. Detail
in §5.

**Literature:** Roland TR-909 Service Notes, First Edition, June 15 1984
(https://archive.org/details/roland_Roland_TR-909_Service_Manual; PDF
fetched to `.reference-captures/tr909/TR-909-Service-Manual.pdf`, 16 pages,
scanned, no OCR text layer — rendered to PNG in-session with PyMuPDF to
read the Block Diagram page visually). This is a genuine circuit source,
not just a schematic archive: the Block Diagram page (PDF page 4) names
every voice's signal path with IC references, and it corrects an
assumption in this dossier's own charter — see §4.

**OSS — visited, corroboration value low:** sonicarchetype/TR909
(https://github.com/sonicarchetype/TR909). Visited this session, including
the LICENSE file
(https://github.com/sonicarchetype/TR909/blob/master/LICENSE: MIT,
"Copyright (c) 2025 SONIC ARCHETYPE"). Turns out to be a **sample-playback**
web drum machine (React/Vite `src/`+`public/`, no oscillator/filter/envelope
code), crediting "jason baker for sounds" — i.e. it plays third-party
samples, it does not model the circuit. It corroborates nothing about
synthesis architecture and is recorded here only because the survey named
it and evidence discipline requires reporting what was found, not just what
was hoped for.

## 3. Hardware structure vs the module

Wikipedia's infobox (https://en.wikipedia.org/wiki/Roland_TR-909, read this
session): **"Polyphony: 11 voices," "Timbrality: Monophonic."** The text
names them: "bass drum, snare, toms, rimshot, clap, crash cymbal, ride
cymbal and hi-hat (open and closed)" — 11 named sounds (BD, SD, 3 toms,
rimshot, clap, crash, ride, open hat, closed hat), and confirms the
split the module already assumes: "The 909 was the first Roland drum
machine to use samples, for its crash, ride and hi-hat sounds" — the rest
is analog synthesis. `NOTE_MAP` (tr909.py:42-54) has exactly these 11
entries; no fallback-branch gap like `tr808`'s congas/maracas.

**But 11 named voices is not 11 independent circuits.** The service
manual's own spec page (PDF page 1, "SPECIFICATIONS" box, Rear Panel)
lists the individual "Multi Out" jacks by name: *"Bass Drum, Snare, Low
Tom, Mid Tom, Hi Tom, Rim Shot, Claps, Hi-Hat, Crash, Ride"* — **ten**
jacks, not eleven, because open and closed hat share one "Hi-Hat" jack.
The Block Diagram page (PDF page 4) shows why: the HI-HAT block has a
single Memory (IC69) → Address Counter → D/A → VCA → Low-Pass Filter →
Amp chain, with "Close/Open" as a control input into the trigger/envelope
logic, not a second signal path. **Open and closed hat are one physical
playback engine**, matching the module's existing choke logic
(tr909.py:184-186, releasing `open_hat_keys` on a closed-hat hit).

The same page shows the **Crash/Ride Cymbal** block with a single Memory
(IC53/63) → Address Counter → Timing Circuit → OSC → D/A → VCA (Q71/Q69) →
Low-Pass Filter chain feeding two output buffer stages (IC65a "Crash Out",
IC64a "Ride Out") — one digital engine, two analog output taps. This is a
**moderate-confidence finding, read from one schematic page, not
cross-checked against a second source or by ear**: Crash and Ride likely
cannot sound truly independently (no second Memory/Address Counter/OSC
exists to drive a second sample simultaneously), unlike the Multi Out jack
list which *does* give them separate physical jacks. Station B should
sanity-check this against the pack's own audio (do any of Audiorealism's
factory-pattern-adjacent files layer crash+ride?) before committing to a
choke; §6 proposes it as the accuracy-forward default, flagged clearly.

So: **11 nameable voices (matches `NOTE_MAP`), 9 independent circuits**
(open/closed hat share one; crash/ride most likely share one).
`MAX_VOICES = 16` (tr909.py:105) is a `synthio.Note` pool ceiling, not a
hardware voice count — same caveat `tr808.md` recorded. Per the unattended
charter, the effective ceiling is **13** resident notes: `synthio`'s core
caps at 14 simultaneous notes program-wide (proven for `tr808`), and
CPython additionally mishandles an at-cap re-press
([audioif#8](https://github.com/PyDevices/audioif/issues/8)) and re-press
phase ([audioif#9](https://github.com/PyDevices/audioif/issues/9)), so 13
keeps every runtime one below the cap on every retrigger. §6 below designs
to that ceiling directly, rather than leaving it for a Station B rescue as
happened on `tr808`.

## 4. Modeling approach, by voice group

**Bass drum — not a bridged-T relative.** The charter's framing assumed a
`tr808`-style resonant filter network; the Block Diagram (PDF page 4)
shows a different circuit: **CV Gen (IC12) → VCO (IC13) → shaper → VCA
(Q12) → ENV1**, with a separate **ENV3** pulling the VCO's CV input down
from an elevated onset toward the `Tune`-set settled frequency, plus an
independent **Pulse Gen (Q8/Q9) + filtered Noise Gen (IC31/32/33) → VCA
(Q6) → ENV2** click layer gated by an "Attack Level" pot. This is a
**proper VCO with a CV pitch-drop envelope**, not a passive feedback
network — the 909 and 808 kicks are different circuits, not variations on
one.

**The two-stage attack question, answered:** no jump is needed. Measured
directly (peak-relative windows, 5–30 ms vs 40–80 ms post-peak, on the
`tune{000,025,050,075,100}-attack100-decay100` grid): early/late pairs are
70.3/46.9, 82.0/46.9, 93.8/46.9, 117.2/58.6, 164.1/82.0 Hz — a single
**downward** pitch sweep from an elevated onset to the settled tune, never
a jump *above* the settled value first. The module's existing one-shot
`FALL` LFO bend on the `body` Note (tr909.py:140-142) is already the right
*shape* for this circuit — unlike `tr808`, which needed a new two-stage
bend added. What's untuned: the drop ratio isn't constant across the tune
knob (1.4-1.5× at tune000 vs 2.0× at tune100), so a fixed `scale=0.8` is a
simplification; consider scaling `drop.scale` with `bd_tune` if tightening
further, but this is a tuning note, not a structural one.

The click layer measures cleanly against the Attack macro: onset peak
dBFS rises monotonically -12.14 → -8.19 dBFS and onset HF-RMS rises 2.13×
across `attack{000,025,050,075,100}-tune050-decay100` — confirms Attack
controls click *prominence*, matching `amp * bd_attack` on the click Note
(tr909.py:145-148). One toolkit note: the schematic mixes the noise
through a **low-pass** filter before the click VCA, where the module uses
a **high-pass** (tr909.py:144); worth a listen-test, not asserted as wrong
outright since the two paths (Pulse Gen + filtered noise, summed) aren't
separable in the block diagram alone.

**Snare drum — two body oscillators, not one.** The Block Diagram shows
**VCO1 (IC37) + VCO2 (IC38)**, each with its own VCA/ENV, mixed at Amp
IC40b — a dual-oscillator tone body — plus a separate noise path (Low-Pass
→ High-Pass → VCA47/48, ENV4/ENV5, CV Gen IC35 setting the HP cutoff — this
is the "Tone" knob's actual target, confirming `sd_tone` maps onto a real
control) with its own "Snappy" pot blending noise into the mix. The module
currently has one tone `body` Note (tr909.py:153) against the hardware's
two; §6 proposes restoring the second VCO as an optional stretch within
budget.

Measured (`SnareDrum909-tune{000,025,050,075,100}-tone100-snappy100`):
f_early 120, 140, 180, 200, 240 Hz — clean, monotonic, close to but
slightly narrower than the module's `sd_tune` range (`logmap(120, 300)`,
tr909.py:212). Tone and snappy sweeps move tau modestly (0.033→0.064 s and
0.066→0.064 s respectively) but leave spectral centroid nearly flat
(~8500-9000 Hz either way) — tau is a usable Tone-knob proxy; centroid is
not. Snappy's real acoustic effect (noise-to-tone *balance*, not the
noise band's own shape) isn't well captured by tau/centroid at all; a
noise-band-energy-fraction metric would serve Station C better than either
number here, flagged rather than invented.

**Toms — tone only, no noise-click layer.** The Block Diagram's
LOW/MID/HI TOM block is three parallel **VCO+VCA+ENV** chains (IC5/21/43,
IC7/24/46, IC9/25/47) with **no noise input anywhere in the block** —
unlike Bass Drum and Snare, which both show an explicit noise path. The
module currently adds a `noise_click` Note per tom hit
(tr909.py:174-177) that has no schematic counterpart. A single shared
"Decay" pot is visible once at the bottom of the tom block, matching the
module's single `tom_decay` macro governing all three toms
(tr909.py:11,172) — good corroboration for that part of the design.

Measured on the full 11×11 tune/decay grids (`{Low,Mid,Hi}Tom909-tune*-
decay*.wav`, decay=100 for the tune curve, tune=050 for the decay curve —
121 hits per tom, all at literal known knob settings):

| Tom | f_late @ tune 0/50/100 (module's macro range) | tau @ decay 0/50/100 |
|---|---|---|
| Low | 60 / 90 / 120 Hz (module: `logmap(60,120)` — matches closely) | 0.059 / 0.095 / 0.125 s |
| Mid | 75 / 110 / 145 Hz (module: `logmap(100,160)` — measured runs lower) | 0.042 / 0.069 / 0.084 s |
| Hi | 90 / 130 / 175 Hz (module: `logmap(140,220)` — measured runs notably lower) | 0.040 / 0.071 / 0.090 s |

Both findings matter for Station B: `tom_decay`'s current `logmap(0.1,
0.8)` (tr909.py:225) overshoots the measured 0.04-0.13 s span considerably,
and the Mid/Hi tune ranges are shifted low relative to today's code.

**Rimshot — filtered noise, not tuned oscillators.** The Block Diagram's
Rim Shot block is **three parallel band-pass filters (F1/F2/F3, ICs
48a/49a/49b) → Clipper (D91/D92) → VCA (Q65) → High-Pass Filter (IC50b)**,
fed from a noise source labeled "Tom Noise" (physically adjacent to the
tom board on the PCB) gated by VCA Q33 — no VCO anywhere in this block.
The module currently uses two **tuned triangle-wave** Notes at 450/1600 Hz
(tr909.py:217-220), which has no basis in the schematic at all — this is
the single largest per-voice modeling gap found in this survey. Measured
stats (n=28, accent sweep) are consistent with a noise-driven click: tau
0.019-0.050 s (short, percussive) and a wide centroid spread (2593-16283
Hz) rather than a settled pitch — `f_early` pins at 220 Hz for every
accent level, which reads as a filter-bank artifact, not a "note."

**Hand clap — one noise/VCA chain shaped by a sawtooth envelope, not three
staggered Notes.** The Block Diagram shows a single Band-Pass Filter → VCA
(IC30) → Amp (IC28) path, with the multi-hit "flutter" produced by a
**Saw Tooth ENV** (IC29/Q40/Q38) modulating the VCA — one signal chain,
amplitude-shaped, not three independent noise bursts. The module fakes the
flutter with three separately-triggered Notes at staggered `attack_time`
(tr909.py:209-211). Confirmed technically feasible to do as the schematic
implies: `Note.amplitude` accepts a block/LFO in this audioif build
(`.venv`'s `synthio.py:_value`/`scaled`, used identically for `bend`
already in this file) — an amplitude-LFO with a multi-bump shape could
reproduce the flutter on one Note. §6 proposes this as the resident-note
budget's biggest single win.

**Hi-hat and cymbals — PCM wavetable-bank synthesis, tune coupled to
decay.** Per Wikipedia and the Block Diagram, these three are genuinely
sample-based on hardware (ROM playback via Memory/Address
Counter/OSC/D-A), which the module already treats as filtered-noise
synthesis rather than PCM — a reasonable proxy given no ROM dump exists to
work from, but worth stating plainly as an approximation, not a claim of
matching 6-bit PCM character. The pack's own **Tune** sweeps show why
pitch and decay move together on real hardware: raising Tune measurably
*shortens* tau as well as raising the spectral centroid (Crash tau
0.275→0.150 s, centroid 8408→11227 Hz across tune 0→100; Ride tau
0.284→0.156 s, centroid 8735→11233 Hz) — consistent with a ROM played back
at a Tune-controlled clock rate (faster clock = higher pitch *and* faster
decay), exactly what the OSC/Address Counter/Timing Circuit blocks predict.
The module's `cym_tune` macro (tr909.py:227) currently retunes a bandpass
center only; it does not shorten decay with it. Closed-hat's decay grid
(`ClosedHat909-decay{000,025,050,075,100}.wav`) measures tau 0.0085,
0.0219, 0.0260, 0.0288, 0.0293 s — a much smaller and more front-loaded
span than the module's `ch_decay` `logmap(0.02, 0.15)` (tr909.py:230).

## 5. The FIXED-CIRCUIT map (mandatory)

Per the unattended charter and the pattern `tr808`'s evidence pack proved:
every voice is a **permanent set of `synthio.Note` objects, retriggered in
place**, matching how the real machine's voltage-triggered circuits work —
nothing allocated at strike time, nothing released mid-play, no tail ever
occupying a slot. §3 and §4 justify each row below directly from the
schematic, not by assumption:

| Voice | Resident Notes | Justification |
|---|---|---|
| Bass Drum | 2 (body VCO + click) | matches the circuit's two chains (§4) |
| Snare Drum | 2 (body tone + noise) | baseline; hardware has 2 VCOs, see stretch note below |
| Low/Mid/Hi Tom | 3 (1 each) | tone-only per voice — the noise-click layer has no schematic counterpart (§4), dropping it from 2/voice to 1/voice |
| Rimshot | 2 (two parallel band-pass noise paths, approximating the schematic's 3) | 3 literal bands don't fit one `synthio.Note`'s single filter slot each; 2 is the controlled simplification |
| Clap | 1 (noise + amplitude-LFO flutter) | the schematic is one signal chain, not three (§4) — biggest single-Note saving |
| Hi-Hat (open+closed) | 1 (shared, retriggered; decay/filter swapped by which key hit) | one physical PCM engine on hardware (§3) |
| Cymbal (crash+ride) | 1 (shared, retriggered; tune/decay swapped by which key hit) | one physical PCM engine on hardware, moderate confidence (§3) |
| **Total** | **12** | 1 below the 13 ceiling |

**Optional stretch, if Station B wants it:** restore Snare's second VCO
(3 Notes instead of 2) to land exactly on 12+1=13, the hard ceiling with
zero margin. Recommendation: ship the 12-Note baseline; the margin is
worth more than the second VCO given how close 13 sits to the proven
CPython at-cap re-press bug.

**The crash/ride choke is the one structural change in this map that is
not a straightforward finding** — it changes audible behavior in any
pattern that currently layers crash and ride, and rests on one schematic
page (§3). It is proposed here because the reference decides structure in
both directions (Brad's rule) and the schematic gives no evidence of a
second independent playback path; but it is flagged, not asserted, and
Station B should verify by ear before the batch listen locks it in.

## 7. MCU budget and macro budget

The fixed-circuit map (§5) holds 12 permanent `synthio.Note` objects,
allocated once at `create()` and never again — down from a worst-case ~21
ephemeral Notes if all 11 voices fired in the same block under the current
per-hit-allocation code (BD 2 + SD 2 + Toms 2×3 + Hats 1×2 + Cymbals 2×2 +
Clap 3 + Rimshot 2). No new oscillator classes are needed: SINE, TRIANGLE,
SQUARE and NOISE tables already exist in the file (tr909.py:69-72); the
clap's flutter uses an `LFO` on `amplitude` the same way the BD's `drop`
already uses one on `bend`. **No `" - lean"` patch is expected** — the
rebuild is a reduction in resident state, not an increase.

`MACRO_LABELS` is already at the 16/16 ceiling (tr909.py:9-13). **No new
macro is proposed**, and none needs folding: every one of the 16 existing
macros maps onto a real front-panel control the schematic actually shows
(Tune/Attack/Decay per drum, a single shared Tom Decay pot, a single
shared Snappy/Tone pair, a single "Cymbal Tune" that now has a schematic
reason to exist — it is the one shared PCM engine's clock rate, not two
independent tunings). If Station B's crash/ride choke lands, `Cymbal Tune`
retains its current meaning unchanged; only the *voice-sharing* changes,
not the macro surface.
